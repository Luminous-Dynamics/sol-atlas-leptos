# IEAC built-environment projector benchmark protocol v0.1

**Status:** proposed qualification protocol. It extends the existing IBAP preregistration work in [#338](https://github.com/Luminous-Dynamics/sol-atlas-leptos/issues/338), dependency coverage benchmark in [#488](https://github.com/Luminous-Dynamics/sol-atlas-leptos/issues/488), and independent traversal oracle in [#484](https://github.com/Luminous-Dynamics/sol-atlas-leptos/issues/484). It is not a benchmark result.

## 1. Do not use one oracle for three different questions

The benchmark requires three independently authored references:

1. **Gold source inventory:** what records and source systems exist within the declared evaluation boundary, including inaccessible, excluded, and unsupported sources.
2. **Gold projection mapping:** how each in-scope native record and relationship should map into IEAC, including identity, payload digest, media type, schema, temporal fields, and explicit losses.
3. **Gold impact oracle:** which downstream engineering artifacts, receipts and decisions become invalid or require review after a frozen change mutation.

The candidate extractor/projector must not author its own gold references. At least one independent reviewer should adjudicate disagreements and keep the candidate implementation blind to held-out mapping cases.

This prevents three common false victories:
- a correct traversal over an incomplete extracted graph;
- a semantically wrong projection that happens to produce a valid IEAC schema document;
- a correct invalidation traversal evaluated against an oracle generated by the same traversal logic.

## 2. Frozen corpus tiers

| Tier | Corpus | Purpose | Admission gate |
| --- | --- | --- | --- |
| P0 | Hand-checkable synthetic cases | Identity and mapping arithmetic, controlled missingness, deterministic replay | Exact oracle agreement; zero false-complete |
| P1 | Frozen open standards and public fixtures | IFC/IDS, QIF, geometry metadata, CAD/BIM exchange | Rights-cleared, byte-digested corpus; two independent parsers/checkers |
| P2 | Held-out project datasets | Generalization across vendors, disciplines, project phases and owner namespaces | Independent data custodian and reviewer; no tuning on held-out cases |
| P3 | Operational pilot | Decisions and revalidation under real change events | Professional review, operational baselines and incident capture |

P0 should begin with 10, 100, 1,000, 10,000 and 100,000 record graphs. Do not claim P1/P2/P3 from synthetic cases.

## 3. Mutation operators

Mutations must preserve as much unrelated structure as possible so a mutation does not become trivially detectable through a malformed file.

### Identity
- same payload, distinct owner namespace;
- same owner namespace and record ID, different revision;
- same identity components, conflicting payload digest;
- duplicate identity component names;
- component-order permutation;
- invalid UTF-8 or non-canonical component name;
- source-native namespace removed or changed.

### Projection and lineage
- omit a source record but leave all remaining nodes valid;
- omit one relationship but leave graph schema and endpoint references valid;
- rebind a parent reference to another content digest;
- change solver input digest without changing the receipt;
- alter a target artifact or authority reference;
- duplicate one endpoint pair with a different native relationship key;
- inject a parent or decision-supersession cycle;
- remove source media type/schema descriptor;
- change the source schema while holding the payload digest constant;
- change the source record ordering while preserving all native IDs.

### Coverage and temporal state
- truncate pagination at a page boundary;
- change source snapshot after extraction;
- mark a source inaccessible or rights-unknown;
- expire an absence assertion between check and evaluation;
- revoke an owner key after an otherwise valid historical receipt;
- change a verifier build or mapping policy after receipt creation;
- move an event's valid time while keeping recorded time fixed.

Every mutation has a unique ID, expected finding, severity, affected native keys, and expected impact set. Store the exact mutation seed and exact base bytes.

## 4. Required metrics and denominators

Do not collapse these into a weighted score.

| Dimension | Metric | P0 target |
| --- | --- | --- |
| Identity | False identity merges | 0 |
| Identity | False identity splits | 0 for stable owner namespace + same native identity tuple |
| Payload | Source payload digest mismatches | 0 |
| Source coverage | Recall against independent gold inventory | 100% on supported declared scope |
| Projection | Node mapping precision and recall | 100% on supported frozen subset |
| Projection | Relationship mapping precision and recall | 100% on supported frozen subset |
| Loss detection | False `projected_without_known_loss` under a loss mutation | 0 |
| Graph | Invalid schema, unresolved endpoints, duplicate endpoint pairs, cycles | 0 admitted graphs |
| Replay | Graph digest disagreement for identical normalized graph | 0 |
| Receipt | Exact input/build/profile/output binding disagreement | 0 |
| Impact | False-negative and false-positive invalidation against full-scan oracle | 0 on bounded P0 cases |
| Reliance | Unqualified `NoImpact` | 0 |
| Safety | Authorization inferred from projection or schema conformance | 0 |

Always report raw numerators and denominators, including the number of unsupported, unavailable, excluded, malformed and timed-out cases. A system cannot improve its apparent recall by excluding difficult inputs without showing those exclusions.

## 5. Baselines and comparisons

Compare at the layer where products actually make a claim:

- **Source and BIM/IDS interoperability:** independent IFC/IDS implementations, frozen IDS 1.0 fixtures, and a separately labelled IDS 1.1 preview lane. A checker pass is not a geometry or structural-safety result.
- **Manufacturing traceability:** compare the data model and cross-organization exchange with NIST IR 8536 principles, retaining the distinction between traceability linkage and proof that a source claim is true. Benchmark against its reference implementation when its code and test corpus are publicly available and rights permit.
- **Digital-twin composition:** compare adapters, schema coverage, identity and synchronization behavior against established iTwin, Siemens and Palantir integration capabilities. Do not compare an assurance prototype to their full products with marketing feature counts.
- **Geometry:** use CGAL exact-predicate/inexact-construction and exact-construction modes, Manifold exact and robust engines, and public pathological mesh corpora. Measure output embedding, topology, volume deviation and refusal—not merely function return status.
- **Impact analysis:** compare full revalidation, immediate invalidation, transitive graph traversal, base-bound sparse deltas and the independently authored full-scan oracle.

Do not advertise a commercial baseline as tested until its exact version, configuration, input corpus, hardware and result artifacts have been run by the benchmark team. Published vendor capability descriptions are context, not comparative test evidence.

## 6. Efficiency and Pareto reporting

Report separately:
- wall-clock p50/p95/p99 and worst case;
- peak resident memory and serialized receipt/graph size;
- CPU/GPU time and energy where measured;
- revalidation count and avoided recomputation;
- refusal, cancellation, timeout and recovery counts;
- deterministic replay under changed thread count and input ordering.

Use a Pareto frontier. Correctness, coverage, refusal quality and worst-group reliability are hard gates. Speed cannot compensate for a false-complete projection, missed dependency or unqualified `NoImpact`.

## 7. External qualification ladder

- **Level 1 — internal synthetic qualification:** frozen fixtures and independently hand-checked oracles.
- **Level 2 — independent implementation comparison:** two or more separately implemented adapters/checkers and adjudicated disagreements.
- **Level 3 — held-out project evaluation:** datasets unseen during development, rights-cleared and reviewed by independent domain professionals.
- **Level 4 — operational evidence:** prospective change events, accepted-work outcomes, real revalidation cost and post-incident audit.

A claim must state the highest level it has actually passed and the exact corpus/version. The current projector work is at the implementation/specification stage; it has not yet passed Level 1.

## 8. How this can beat the state of the art

The proposed differentiator is not merely a faster graph or another digital twin. It is an independently auditable chain that can identify which claim is supported by which source, explain every known loss, distinguish missing evidence from negative evidence, and determine which engineering conclusions must be revalidated when evidence changes.

The defensible competitive target is:
- correctness equal to the strongest independent reference on supported cases;
- better cross-vendor identity and relationship preservation;
- explicit and machine-checkable loss/unsupported-feature behavior;
- selective revalidation with zero missed invalidations against a full-scan oracle;
- lower cost and latency only after the correctness and coverage gates remain satisfied.

That is a testable path to differentiation, not a claim of superiority before evidence exists.
